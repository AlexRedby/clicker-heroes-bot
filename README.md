# Clicker Heroes bot

Go bot for a running Clicker Heroes game. A single `run` handles fish collection, hero levels, active skills, progression, earned gild gifts, mercenary quests, Ascension and fresh-save Ancient purchases. `-progression` enables the complete growth and Ascension cycle, including heroes, skills, owned Auto Clickers, earned gifts, useful gild redistribution and fresh-save Ancient purchases. Mercenaries are independently enabled with `-mercenaries`; fish collection is always active and progression assists monster clicks when purchase or navigation work is unavailable. The normal progression loop equips clear Active relic improvements. Progression redistributes gilds when useful and clears the native Ascension Junk Pile blocker. Automatic Transcension and Outsider purchases require the separate `-transcension` option.

## Requirements

- **macOS:** Install Go (`brew install go`), Xcode Command Line Tools (`xcode-select --install`), and OpenCV 4.13 using the [GoCV macOS instructions](https://gocv.io/getting-started/macos/). Grant the app that runs the bot (for example, Terminal) **Accessibility** and **Screen & System Audio Recording** permissions in System Settings > Privacy & Security.
- **Windows:** Install Go (`winget install Golang.Go`) and GCC to build RobotGo (`winget install BrechtSanders.WinLibs.POSIX.UCRT`). Make sure the directory containing `gcc.exe` is in `PATH`.

Fish detection uses GoCV 0.43.0 with native OpenCV 4.13. Install OpenCV before building on every platform; see the [GoCV installation guides](https://gocv.io/getting-started/). On macOS or Linux, verify it with `pkg-config --modversion opencv4` (expect 4.13.x). Also check `go version` and `gcc --version`. If `shot` reports `Capture image not found` on macOS, enable Screen & System Audio Recording for Terminal (or the built app) and restart it. The `click` and `run` modes also require Accessibility permission.

Hero leveling, automatic progression, Ascension and Ancient purchases additionally require the `tesseract` executable with English OCR data in `PATH`. Enable **Always use scientific notation** in the game's settings so gold, prices and damage use the same readable format.

Ancient calculations run inside the Go application. The game data is embedded in the binary; no additional runtime or project-directory files are required for the calculator.

An informational Transcension preview is available in the same executable:

```sh
go run . -mode transcension-plan -save "path/to/fresh-save.txt" -out artifacts/transcension-plan.json
```

It reports estimated Ancient Souls/TP, closed Ascension history, affordable Outsider additions and a separate ideal allocation that may require respec. The active allocation supports fewer than 21000 total AS; higher budgets still get state and reward estimates. Gains, TP and respec behavior need comparison with the installed game's UI. Save history does not establish active-play time or a combat wall, so the preview cannot authorize a reset. It preserves the save and makes no game input; omit `-out` to print JSON. Fresh Ancient plans also include this preview, so `run -export-dir` reports it automatically without another process. Pure calculator tests in `internal/ancientcalc` need Go only; the main executable requires OpenCV.

While `run` is active, manually opening the Outsiders tab prints a read-only report of its AS wallet/reward, displayed TP, sacrificed souls, next-AS threshold and complete visible cards with levels and FEED costs. Costs retain the selected quantity (including MAX). Recognition is calibrated against the 1.0e12-6144 frame and checked at 1280/1920/2560 widths; other skins and unreadable fields remain unknown. Reports reuse the shared capture, read at most once every five seconds and discard results after context changes or F8. This does not click Transcend or FEED, scroll the list, or verify reset/respec behavior.

With `run -save`, `-ancients-save` or a successful `-export-dir` export, the report also shows concrete Outsider additions from the current wallet and a separate conditional plan after the displayed AS reward. It checks visible levels, wallet, TP at display precision and fixed-quantity FEED costs against the save/model; hidden levels still come from the save and MAX pricing remains unverified. State/cost mismatches suppress the plan. A changed reward is reported explicitly and the conditional plan uses the UI reward. These checks do not establish save freshness or authorize spending/reset. Missing prestige metadata remains advisory to ordinary Ancient/relic automation.

The optional `run -progression -transcension -export-dir "path/to/export"` enables the prestige controller through the shared capture, export and input queue. A live combat wall, useful Ancient Soul reward and fresh save are required; historical save timestamps alone cannot trigger a reset. Recognized reset controls and affordable fixed-quantity FEED controls allow input, followed by exact fresh-save receipts. A profile-bound journal preserves unfinished reset/purchase ownership across F8 and restart; uncertain input is reconciled before another purchase. Restoration reuses hero setup, progression and ordinary Ancient allocation. Unsupported Ancient summon controls save `artifacts/transcension-summon-*.png` and pause for calibration. Automatic respec is excluded. Fixture checks do not establish installed-game acceptance. Ordinary `-progression` does not enable Transcension. The `Transcension preview: ... informational only` line belongs to the offline calculator; actual runtime decisions and stages use the separate `Transcension:` log prefix. A preview marked `insufficient_evidence` is not a runtime disable switch.

To inspect the same plan offline with an existing Outsiders image:

```sh
go run . -mode transcension-plan -save "save.txt" -screenshot "outsiders.png" -out artifacts/outsiders-plan.json
```

Omitting `-screenshot` preserves the original save-only preview. This image check requires Tesseract, makes no game input and preserves both input files, including their hardlink/symlink aliases.

## Integrated run and game checks

Update the checkout on the computer running the game, then launch:

```powershell
git switch main
git pull --ff-only
go run . -mode run -progression -mercenaries -export-dir "C:\path\to\save-folder" -stats
```

Replace the export folder with the existing folder opened by the game's Save action. The folder is required for `-progression`; there are no separate `-hero-levels`, `-skills`, `-auto-clickers`, `-gilds` or `-ascension` switches. `-mercenaries` remains independent. A plain `run` collects fish; `run -mercenaries` adds quests without hero or reset automation. Keep the game in English, enable **Always use scientific notation**, open Heroes and focus the game before pressing F8. The run has no time limit or startup delay. Progression reads the available/owned pool and uses `C` + click to assign free owned clickers. With multiple clickers it reserves one for Buy Available Upgrades and assigns the others to the monster; a sole clicker goes to the monster. Existing assignments are preserved and no clickers are purchased. Progression assists clicks in the recognized monster area when otherwise idle, including while hero OCR is unavailable. `-x/-y` optionally select a target for continuous bot clicks. Add `-windowed` only for the optional windowed mode.

1. The first F8 with `-progression` acquires a fresh Save export from `-export-dir` before preparing heroes. It skips the hero sweep when the required upgrades are already bought, or goes straight to Buy Available Upgrades when the required levels are sufficient. Missing levels/hires and unsupported hero data use the bounded visual sweep, which levels only HIRE and positively level-locked rows. During setup it enables progression and uses the Ancient plan from that same initial export; it does not export a second time. Unavailable Ancient/prestige data does not block hero setup. Owned/free Auto Clicker counts are checked every five minutes after placement; freed clickers and resolved failed attempts are reconsidered, with C held for 200 ms before clicking. A recognized disabled upgrade footer can also receive an owned clicker. A confirmed footer Auto Clicker assignment completes the upgrade pass; a failed assignment falls back to a fresh footer read and ordinary click. A previously confirmed footer clicker skips this pass. An unreadable or covered footer is sought for 10 seconds; a final drag or freshly recognized footer can use a fixed additional two seconds. Normal play and periodic upgrade checks then continue. Empty plans continue on Heroes without opening Ancients. Confirm `save export: fresh initial save ready` on the first startup, `save export: fresh plan ready` after Ascension, and `submitted Ancient ...` for planned purchases. The batch returns to Heroes and continues ordinary automation.
2. Confirm the bot scrolls to the latest hero, logs `leveled hero ...`, collects visible fish, uses skill hotkeys and enables/retries progression. Mercenaries and earned gifts run when their notifications/checks are due. Test F8 pause/resume while the game has focus.
3. At a confirmed combat wall with meaningful soul gain, Ascension checks relic equipment through a fresh export, drags clear Active improvements into the four slots and verifies the batch through a new export. Improved equipment gets another combat attempt before Ascension evaluates its reward dialog. After zone 1 it starts heroes/progression, clicks Buy Available Upgrades, exports and buys Ancients, then continues playing. Free owned Auto Clickers are assigned again after the confirmed reset. If the native Junk Pile blocker appears, the bot salvages its junk once and continues Ascension; equipped relics are untouched.
4. Stop with Ctrl+C and retain the final `pipeline:` counters, relevant action/error logs and `artifacts/*failure*.png`. Native Windows timing and game behavior still need these live checks; passing fixture tests is not native acceptance.

To validate startup, provide full-resolution frames before and after startup hire/skill inputs if an upgrade stays locked, plus logs for the skill sweep and bulk button. To validate Auto Clicker placement, retain the before/after available pool count and a frame showing the monster/footer assignments; keep before/after frames and logs if the Junk Pile salvage or Ascension transition fails. A fresh Save export from that state helps connect IDs, levels and unlocked upgrades to the UI. No extra reset is needed solely for screenshots.

Relic recommendations are also available without game input:

```sh
go run . -mode relics-plan -save "path/to/fresh-save.txt"
```

With `-progression -export-dir`, relic equipment is checked at startup, on the yellow Relics notification and before automatic Ascension. The startup export is reused. Each proposed replacement is evaluated against the complete current outfit and saved Ancient/Outsider levels. Its Active priority is: fewer monsters at the highest reached zone, Primal Boss chance, continuous Lucky Strikes/Golden Clicks, other skill uptime, cooldown reduction, then boss timer, chest chance, hero cost, gold/ruby chances, boss life reduction and damage/gold bonuses. Useful caps include two monsters, guaranteed Primals and skill duration reaching that skill's cooldown. Ties and negligible gains preserve current equipment. Minimum improvements include 0.01 boss-timer seconds, 0.01 percentage points for chance effects and 0.1% for damage/gold multipliers. Each individual move must pass its threshold; hypothetical gains from multiple insignificant swaps do not trigger a batch. This is an explicit priority policy, not an optimal run simulator.

Only candidate tooltips need OCR. The bot drags at most four cards per batch; a fresh export verifies changed equipment before cleanup. Ordinary Junk Pile cleanup runs only when every remaining item is no better than a retained equipped item in every supported Active bonus; exact decimal comparison preserves small real advantages. Tradeoffs are retained and hovered to acknowledge the notification. Unsupported effects, ambiguous identities, changed inventory and unfinished equipment prevent cleanup. The native reader supports six visible junk cards; larger or obscured inventories defer the visit while play continues. Forge Core upgrades and ruby spending are not performed. Advisory modes remain read-only. An owned automatic Ascension may discard the remaining junk through its recognized native warning after equipment preflight; orphan prompts after F8/restart are cancelled.

## Run

From the project directory:

```sh
go mod download
go run . -mode help
go run . -mode shot
go run . -mode click -x 700 -y 400
go run . -mode run
go run . -mode run -mercenaries
go run . -mode run -progression -export-dir "C:\path\to\save-folder"
go run . -mode run -progression -export-dir "C:\path\to\save-folder" -mercenaries -stats
go run . -mode run -progression -export-dir "C:\path\to\save-folder" -duration 10m
go run . -mode run -x 700 -y 400 -interval 100ms -fish-interval 1s -duration 10m
```

The example coordinates are placeholders. Use pixel coordinates from the saved screenshot of the primary display for `-x` and `-y`, including on Retina displays. The bot validates these coordinates and converts screenshot pixels to desktop points on macOS. By default, `shot` saves `artifacts/screenshot.png` and creates the directory if needed. Put other generated test files in `artifacts/` too; Git ignores this directory. You can choose another screenshot path with `-out`. After starting `shot` or `click`, you have 5 seconds (`-delay`) to switch to the game. `run` has no startup countdown; focus the game and press F8 when ready. For `click` or optional monster clicks in `run`, use coordinates inside the monster area.

Opt-in `-windowed` supports a visible game window on Windows/macOS, including a secondary display. Start with `go run . -mode shot -windowed`, then use `go run . -mode run -windowed -progression -export-dir "C:\path\to\save-folder"`. The screenshot contains only the verified viewport; `-x/-y` in windowed mode use pixels from that crop. After a resize, restart with coordinates from a new viewport screenshot if monster clicks are enabled. Without `-windowed`, coordinates and capture keep their primary-display behavior.

Windowed detection verifies the HUD inside the client area or a centered/bottom-aligned 16:9 game area. Specific recognized game dialogs can also establish the viewport at startup. Unknown/ambiguous geometry and windows clipped or spanning displays suppress input while observation retries; lost focus can return to the previously recognized game window. Window movement or DPI changes discard queued decisions. macOS requires Screen Recording and Accessibility, plus Input Monitoring for the global F8 hook; Windows requires 64-bit Windows with per-monitor DPI awareness support. Cursor readback is checked before mouse-down. Native click/drag, permissions and mixed-display behavior still require validation in the installed game; fixture tests only establish recognition and coordinate math.

`run` starts paused: press **F8** to start, and press F8 again to pause or resume from any window. On some Mac keyboards, press Fn+F8. Pausing blocks new input and invalidates decisions from earlier screenshots. An OCR or detection call already in progress can finish, but its result cannot trigger input after pause/resume. Without `-duration`, it runs until Ctrl+C; a positive `-duration` sets a wall-time limit that also counts while paused. If F8 does not resume the bot, check Accessibility permission for the app running it. Pause before switching away from the game. When native foreground identity is available, input requires the same foreground game process/title observed in the screenshot; if unavailable, the bot reports its visual-context/F8 fallback. This guard does not distinguish windows with identical process/title.

Navigation is shared by all features. Recognized interrupted/manual Settings, quantity, Ascension, junk salvage, quest and Mercenary confirmation dialogs use their close/No controls; unowned tabs return to Heroes when progression needs it. Missed navigation clicks retry at most once per second from fresh frames. Save export retains an acknowledged file baseline across F8 and retries focus restoration if Explorer steals focus again. Unknown or temporarily unavailable frames keep observing without gameplay input. Only recognized game controls are clicked; unsupported dialogs need new recognition evidence. Navigation never confirms purchases, prestige resets or salvage.

Fish detection uses the [Clicker Heroes Orange Fish image from StickPNG](https://www.stickpng.com/img/games/clicker-heroes/clicker-heroes-orange-fish), listed there for personal use only. A detected fish stays suppressed through small position changes and isolated missed detections; three consecutive fish-free scans rearm collection. If the fish is still recognized after five seconds, the bot retries the click. Fish clicks use the same 100 ms press and release-settling wait as hero purchases. A known fish has input priority over hero and Ancient interaction; other recognition and actions do not wait for a completed SIFT scan. Fish scanning continues on every ordinary game tab during pending transactions and slow OCR/export reads. A collected obstruction invalidates panel observations so controls are read again. Popup windows, settings and Explorer suppress fish input while retaining its known position; collection resumes on the next ordinary game frame. Viewport changes discard old coordinates. Mouse/key gestures remain serialized; a native drag or held-key click finishes and releases its inputs before another click. `run` extracts SIFT features from the fish image and each screenshot, matches them with OpenCV, and clicks the center of a fish when enough matches agree on its position, size, and rotation.

With `-progression`, `run` verifies the full-screen Heroes layout, drags the scrollbar only when needed, and requires a confirmed bottom position. Thumb candidates must have a narrow rectangular shape with aligned sides, so the orange fish is not accepted as a thumb. RobotGo smoothly drags the thumb to the bottom edge of the display with the mouse button held, using 0.5-1.5 ms library step delays for faster smooth movement. F8 takes effect after an ongoing library drag finishes and releases the button. It considers the latest hero and its successor. A missing or obscured row skips the purchase; it never falls back to an earlier owned hero. Keep the Heroes tab open and the game filling the primary display. Lists without a recognizable scrollbar are currently skipped.

Initial startup first checks hero levels and purchased upgrade IDs in its freshly acquired export. A completed setup skips the sweep and bulk purchase; only an eligible free UI-observed Auto Clicker may need the footer pass. Missing upgrades with sufficient levels go directly to the bulk footer. When levels/hires are missing, hero data is unsupported, or a confirmed Ascension starts over with little gold, startup sweeps the Heroes list from the top for missing hires and level-unavailable upgrades. OpenCV recognizes HIRE/LVL UP captions and the dark unavailable-upgrade placeholder in each row's bounded strip of the shared screenshot. An owned hero receives levels only when that placeholder is present; purchased checks and hero names are not read. Unlocked icons, including gray artwork and unpurchased upgrades, do not cause extra leveling. Missing hires and rows with a level-unavailable upgrade get at most two Q/MAX inputs per viewport, buying the maximum affordable quantity before the cursor advances. The sweep uses only a viewport cursor and attempt count, with no numeric-level OCR or named roster. It then buys newly available upgrades with the bulk footer; there is no initial trip down to buy upgrades.

The bot keeps the persistent purchase quantity at `x1`, cycling with `T` only if another quantity is selected. It reads gold and the next price from cropped regions, then holds `Q` only during the hero purchase click to buy MAX levels. Hero purchase clicks hold the left button for 100 ms and wait 100 ms after release before moving the pointer or releasing `Q`. Both held inputs are released on errors or cancellation; no MAX selection screenshot is needed. When the next hero costs at most ten times current gold, it waits to buy that hero; otherwise it buys MAX levels of the current hero. It moves the cursor away from hero buttons to dismiss tooltips, then confirms a purchase by reading an increased `Lvl` value with a stable list position. Overlay or animation pixel changes alone do not count. OCR has a configurable three-second limit per execution (`-ocr-timeout`, for example `-ocr-timeout 5s`) and is cancelled when the run stops. Each Tesseract process is limited to one OpenMP thread to avoid competing thread pools alongside SIFT. Gold, price and baseline level share one screenshot and use at most two concurrent Tesseract processes. Confirmation reads only the selected row level and geometry.

After the skill sweep, the bot buys available upgrades again, then continues ordinary latest-hero leveling. Starter monster clicks run only when a shared observation proves insufficient gold, no affordable purchase and no passive hero; pending input and unknown observations suppress these clicks. F8 preserves the bounded sweep cursor, while a confirmed Ascension resets it. Ordinary play checks the upgrade footer every 30 seconds unless a footer Auto Clicker assignment has been confirmed. A recognized disabled footer requires no click. Ordinary Q purchases still confirm an increased numerical level, save timestamped failure frames and stop after three consecutive failures; fish detection continues independently. The [hero progression plan](docs/hero-progression.md) describes recognition and its limits.

During progression, OpenCV recognizes ready skill icons; clock overlays and outer glow identify cooldowns, active buffs and energized buffs. Ready short-cooldown skills run independently. The bot refreshes ongoing energized buffs and prioritizes Lucky Strikes + Golden Clicks + Energize + Reload (`3,5,8,9`) when all four are available. Each activation is confirmed from a fresh frame before continuing the combination. Reload prepares a second wave after the current effects finish.

When the pair is unavailable, Energize can strengthen an available core buff, or Reload can follow a confirmed Golden Clicks cast. F8 or an unexpected observed skill activation interrupts a combination. On restart/resume, an ambiguous Energize charge is consumed by a recognized ordinary buff before new utility combinations. Dark Ritual runs separately without Energize/Reload; the game enforces its 20-use limit. A missed/no-op activation retries after 30 seconds without stopping other skills.

Each key is held for 100 ms and released on cancellation/errors. All native input uses one executor; skill analysis and confirmations continue independently of SIFT. Skills do not require timer OCR or Ancient cooldown formulas. Keep the full-screen game HUD visible.

With `-progression`, the bot recognizes the boot toggle and reads the zone from a cropped HUD region every two seconds. It reuses the skill states from the same frame; activation confirmation checks only the boot icon. A known farm state gets one initial attempt to enable progression with `A`; a missing or obscured toggle is skipped. Activation is visually confirmed. An unconfirmed toggle waits at least 30 seconds before another attempt from a fresh farm frame.

An observed progression-to-farm fallback before a boss records that wall. The bot waits for at least twice the displayed damage proxy (the larger of DPS and click damage), or a previously untried active Lucky Strikes/Super Clicks buff, including Energize. It retains the highest observed damage and combat buffs from the failed boss, so expiration and renewal of the same buff do not alone trigger another attempt. Ordinary retries after repeated failures wait 1, 2, 4, 8, then 15 minutes. A previously untried full combat window (active skills `1,2,3,7`) bypasses this delay; after a confirmed full-combat loss, doubled damage or a new stronger combat buff can also retry promptly. This is a retry heuristic: it does not measure click rate or predict a guaranteed kill from boss HP and the timer. Keep monster clicks or in-game Auto Clickers active for a clicking build. F8, restarting the bot or observing a drop of more than one zone starts a fresh boss assessment, so a new observed attempt can authorize a reset. Fish collection keeps priority; hero purchases and skills continue while farming.

During progression, an observed boss loss after skills `1,2,3,7` overlapped in two boss observations at least two seconds apart starts a World Ascension assessment immediately. Unknown/locked skills and a farm-frame retry baseline do not count as an observed full combat fight. If that proof is unavailable, `-ascension-stall` supplies a three-minute fallback without higher-zone progress. A running boss retry or a fresh stronger retry decision defers the reset. This is a wall heuristic, not a guaranteed optimal Ascension route. It follows the game's [progression guidance](https://blog.clickerheroes.com/how-to-progress-through-clicker-heroes-zones/) to ascend when a boss remains out of reach after skills and upgrades.

Only a reset candidate reads the banked and pending Hero Souls, from two small crops in a shared screenshot. The pending reward must be positive and at least 25% of the soul capital (`-ascension-min-gain 0.25`). Automatic `-export-dir` acquisition supplies the soul baseline, including souls invested in Ancients. An optional `-save "path/to/fresh-save.txt"` supplies an initial baseline before that acquisition. The local calculator supplies the exported wallet plus the sum of owned Ancients' `spentHeroSouls`, never the lifetime sacrificed-souls total. This exported capital remains a floor after a planned Ancient purchase batch; the larger of it and the current bank is used. Automatic acquisition refreshes this baseline after a reset; export again after manual soul spending. If the save lacks spending data, the bot uses the HUD bank. The gain threshold is adjustable and is not an estimate of future DPS. Small/zero gains defer the reset and suggest reviewing Ancient allocation and Transcension; they do not authorize Transcension.

Ascension is part of `-progression`. A disabled toggle by itself is insufficient. Pending inputs, stale damage/reward observations or unreadable soul values defer input; known fish collection has queue priority. Transient OCR gaps and same-window tab/modal visits preserve the wall history, but a fresh progression observation is required before opening the dialog. Successful hero purchases and ordinary skills no longer repeatedly postpone a proven wall by ten seconds. F8, a changed display/window, or an observed manual zone drop clears the Ascension assessment.

The bot clicks the recognized right-hand red spiral, independently reads the reward from the specific Ascension dialog, and confirms with its green `Yes` only if the reward still meets the minimum gain. A manually opened Ascension dialog is never automatically confirmed. A recognized Junk Pile blocker belonging to this transaction receives one Yes, then the bot waits for closure and resumes the normal reward validation. If the client returns to Heroes, it reopens Ascension. An orphaned Junk Pile prompt after F8/restart receives No. Recognition matches fixed text and controls without OCR of the Forge Core amount; equipped relics are untouched. All background actions are suspended during this transaction, and the reward must remain visible and unchanged before confirmation. It does not use `Buy Quick Ascension`, spend rubies or transcend. A missed transition returns to shared navigation recovery after twenty seconds. Following a confirmed return to zone 1, `-progression -export-dir` performs the bounded MAX skill setup, buys newly unlocked upgrades and starts progression as soon as passive damage is recognized. The startup sweep does not OCR hero names or levels; ordinary play levels only the latest available hero. A fresh export and Ancient plan follow the upgrade/progression handoff. The game bulk buyer excludes Ascension. Combat/progression continues during Ancient spending; input stays serialized and popup windows suppress fish clicks. Startup retains its cursor across F8 and pauses with a reason if a stage cannot finish within five minutes. `-progression` requires `-export-dir` at launch so the cycle can continue after reset. Free owned clickers are assigned again after the reset. Fixture tests cover startup and handoffs; two complete native cycles still need live verification.

### Ancient purchases

Export a fresh save using the game settings. Preview an Active-build allocation without game input:

```sh
go run . -mode ancients-plan -save "path/to/clickerHeroSave.txt"
```

The bot includes a Go port of the [MIT Ancient calculator](https://github.com/tomcur/ClickerHeroesCalculator). It uses saved Ancient/Outsider levels and current Hero Souls, excludes pending Ascension rewards, and keeps the Active calculator's economic soul-bank allocation without an extra percentage reserve by default. `-ancient-reserve` optionally sets a spending floor as a percentage or an absolute scientific value; `-ancient-skill-rate` sets the skill-Ancient allocation from 0 to 1 (default 1). Set `-ancient-beyond8k` if your best hero is levelled beyond 8000, matching the calculator's Wepwawet setting. Large quantities stay decimal strings. Allocation uses 384-bit arithmetic, the Active allocation formulas and search with conservative bounds for client purchase pricing and balance rounding, and purchase inputs truncated downward to six significant digits. After allocation and input truncation, non-exponential Ancients at level `1e9` or higher require an entered increase of at least 0.1%; smaller residual purchases are omitted. Small levels and exponential Ancients keep useful `+1` purchases. The Active allocation is an approximate model for damage, gold, farming and skills. If Morgulis is owned, a separate check may use the remaining spendable souls for a profitable purchase: it compares the actual entered quantity and guarded cost against leaving the souls unspent, using the native bonus `1 + 0.10 * unspent souls + 0.11 * Morgulis level`. It merges an existing Morgulis purchase and preserves the spending floor and 0.1% minimum. Without Morgulis, the model retains its calculated soul bank. The native suite checks frozen allocation formulas, independent client-price vectors and reserve invariants, including a `1e1000` soul budget. The preview is saved to `artifacts/ancients-plan.json`. Manually supplied saves are read only; automatic acquisition cleans up its own new export as described below.

Run one purchase batch before ordinary automation:

```sh
go run . -mode run -ancients-save "path/to/clickerHeroSave.txt"
```

Start on Heroes or Ancients in the English full-screen layout, with Ancient cards expanded, and press F8. The bot takes its soul budget from the fresh save and visits Ancients, seeks the remaining purchases by canonical names in the alphabetically ordered list, holds `V` while clicking an owned Ancient, enters its calculated quantity, and clicks OK once. A newer shared frame with that dialog closed and the ordinary Ancients tab recognized marks the item as submitted; it does not verify the resulting level with OCR. Navigation uses one native wheel notch at a time, reads names from the next shared frame, and uses recognized scrollbar-arrow clicks when a target is clipped, bracketed or overshot. A wheel notch is not assumed to equal one card. Two confirmed wheel no-ops switch that target to recognized scrollbar-arrow clicks; those clicks retain shared-frame name feedback and bounded stopping. Only complete purchase buttons with readable names and levels are eligible; an illustration can extend beyond the viewport. Before each next purchase, a full read checks its saved level. The remaining budget is calculated exactly from saved Hero Souls minus guarded costs of submitted purchases and must cover the next cost plus reserve; the wallet HUD is not read. Quantities are truncated downward to at most six significant digits to fit the input field. After typing, the bot waits at least 200 ms, checks that its quantity dialog and OK button remain visible, and confirms without reading the text field with OCR. Fish collection remains active on the Ancient tab and preempts pending purchase/scroll confirmations. Quantity and other popup windows cover fish, so no fish click is sent until the main game screen is visible again. Other automation waits during the visit. The bot returns to Heroes and resumes ordinary automation without repeating submitted purchases.

A closed quantity dialog can acknowledge a submission even if the game did not raise the level, so a silently failed purchase can underbuy. Submitted items are never replayed. Missing/unreadable names, no movement and repeated direction changes stop after bounded retries, with the target, direction and readable neighbors in the log. An unreadable or changed row before a purchase, insufficient calculated budget, a dialog that stays open, an unknown/foreign context or F8 interruption pauses purchases. Logs identify each input stage, the entered quantity and the cause of a timeout. A blocked batch stops Ancient purchases, safely cancels an owned quantity dialog and returns to ordinary gameplay. F8 remains available; it never replays the stopped batch. A fresh export and new plan are required before another batch. It never summons or respecs Ancients, imports/edits saves or spends rubies. Progression manages free owned clickers; the hero-startup/spending handoff uses `-progression -export-dir`. Screen recognition and transaction checks are tested against supplied frames; native purchases need a live game check.

For automatic export, specify the existing folder where the installed game writes its saves:

```sh
go run . -mode run -progression -mercenaries -export-dir "C:\path\to\save-folder"
```

`-export-dir` replaces `-ancients-save`. Before initial hero/upgrade setup (at any zone), after hero setup following a confirmed Ascension, or immediately in an export-only run without `-progression`, the bot opens the menu, clicks the recognized `Save`, restores the original game process after Explorer opens, closes the menu, then reads a new or changed `clickerHeroSave*.txt`. It snapshots the folder immediately before Save, ignores unchanged old files and waits for a stable, fully decodable export. Raw save contents stay in memory; the plan contains allocation data only. The export folder must already exist. After decoding, the bot deletes only the newly created export absent from its pre-Save snapshot and still matching the consumed bytes. Pre-existing, manually supplied, changed and failed exports are preserved. This mode requires foreground game process identification; ordinary input never reaches Explorer. Fish collection remains active when the main game screen is visible, including while the fresh export is read; settings/dialogs and Explorer prohibit fish input. Other automation waits during acquisition and purchases. Export failures explain the stage, foreground/menu recognition and save the latest shared frame to `artifacts/save-export-failure-*.png`, then pause; focus the game and press F8 to retry. F8 cancels acquisition, while interruption of an already started purchase batch still requires a fresh restart. An empty Ancient plan skips the tab visit; a purchase batch returns to Heroes and continues. Existing Auto Clicker assignments are preserved.

During progression, the bot checks the earned gift icon every five minutes (`-gild-interval`, for example `-gild-interval 10m`), starting with one check when the run first starts after F8. It clicks the gift, opens the central chest, selects the visible `Open All`, then closes the Gilded Heroes result panel. If a single reward has no `Open All`, it closes the reward using its visible X. Recognition uses small fixed screen regions and OpenCV templates, without OCR or extra captures. Fish, skill, progression, hero and monster actions are suspended while these windows are open; old panel observations and queued actions are discarded at each transition, while a known fish position is retained until the windows close. Missing/unknown controls are skipped, and an unchanged transaction switches to safe navigation recovery after three repeated clicks or twenty seconds. Verified close controls retry on fresh frames while ordinary gameplay resumes once the dialog is gone. It only opens earned rewards and never uses `Get More`, ruby purchases or gild transfers. As with hero recognition, keep the game full-screen on the primary display.

With `-mercenaries`, the bot recognizes the notification over the penultimate tab, collects rewards, sends idle mercenaries on new quests, checks the bottom of the roster, and returns to Heroes. It can also service a Mercenaries tab left open manually. The visible roster is read once per viewport. Collect and Start Quest use the saved row position; after selecting an offer, the bot presses `Okay` following a fixed 300 ms delay without re-reading countdowns. Game input underneath quest and recovery dialogs is suspended. F8 cancels the pending visit; an interrupted quest dialog is closed and a recognized orphaned recovery prompt receives No before resuming.

Recognized free recruitment quests up to eight hours are preferred; automatic vacancy tracking and recruitment-completion recovery are not implemented. Otherwise, ruby quests follow `4h > 2h > 1h > 30m > 15m > 8h > 5m`; short non-ruby quests precede 24h/48h ruby quests, following the [community ranking](https://clickerheroes.fandom.com/wiki/General_Tips). Dead cards are recognized by their tombstone portraits before their frozen timers are read. Only dead-card rank and bonus text are read for recovery. The bot uses the [community ruby-farming revive ranges](https://ch.jehare.nl/guide/): levels 2-8 without a ruby bonus, or a higher ceiling for stronger ruby bonuses. It revives worthwhile mercenaries using the price and ruby balance shown in the native confirmation, keeps them for later if funds are insufficient, and buries mercenaries outside the paid range. A recognized recovery prompt receives Yes once; after it closes, the roster is read again because card positions may have changed. Unknown traits never authorize burial or spending. Mercenaries with remaining extra lives are deferred until their native chooser is verified. Paid rerolls, paid recruitment and candy canes are excluded. Recognition uses the English full-screen layout shown in the test screenshots; unreadable states end the visit and retry later.

Screen capture has one owner. Fish, skills, progression and due hero analysis consume immutable shared frames in separate bounded workers, each with one running job and one replaceable waiting frame. Results update state as they finish; slow SIFT does not delay other features. A found fish position is cached until collection, so tabs and covering modals do not require another scan. While a position is known, no new fish scans are scheduled; input waits only for the main game to be visible. One deduplicated priority queue feeds sequential input, with fish first. Confirmations consume later shared frames rather than starting private capture/retry loops. A tab, layout, foreground identity or F8 generation change cancels stale decisions. Ordinary capture waits up to 250 ms after the previous capture finishes; slow capture does not immediately trigger another screenshot. Capture also waits during native input and brief UI settling (150-200 ms), so it does not observe a half-drag or temporary Q modifier. `-fish-interval` is a scheduling interval, not a promise that SIFT finishes that quickly. `-stats` prints capture/analysis counts, total durations and discarded stale results when the run stops. Recent p50/p95 timings use at most 256 samples per capture, context reader, analyzer and queue. OCR reports semaphore waiting separately from execution. `wait-polls` counts observed pause, input, settling, modal, confirmation and idle states; these counts are not time durations. See [Automation pipeline](docs/automation-pipeline.md).

The [game hotkey reference](docs/hotkeys.md) records keyboard actions, target tabs and sources for future features.

## Check the project

```sh

```

On headless Linux, run tests with `xvfb-run -a go test ./...` because the keyboard hook needs an X display. `Dockerfile.gocv` includes OpenCV and Tesseract with English data and sets `REQUIRE_OCR_TESTS=1`, so missing OCR dependencies fail the test suite. For a native test environment, use `REQUIRE_OCR_TESTS=1 go test ./...` to require OCR checks too. When running `xvfb-run` as a Docker command, use `docker run --init` so its X server startup signal is handled correctly.

## Project layout

The project uses one Go module and keeps `go run .` and `go build .` as its entry points.

```text
main.go                     Command launcher
internal/bot/               CLI, shared pipeline, navigation, input and game controllers
internal/vision/            OpenCV templates, alpha masks, SIFT fish detection and embedded assets
internal/ancientcalc/       Save decoding, Ancient allocation and prestige/build calculations
internal/achievementgoal/   Achievement goal rules
internal/rubybudget/        Persisted ruby allowance and purchase ledger
internal/timelapse/         Forecast and purchase policy
testdata/                   Shared screenshot regression corpus
```

`internal/bot/input.go` owns cancellable input waits and held-key clicks. `list_scroll.go` owns common list scrolling and scrollbar recognition; `navigation.go` owns recovery to known game screens. Feature controllers retain their own targets and completion rules. `internal/vision` consumes images and returns recognition results; it does not capture screens, send input or depend on the bot coordinator. Its assets are embedded, so the executable does not require the source folders at runtime.

`go.mod` declares dependencies and `go.sum` records their checksums. The calculator remains independent of native vision and input. Calculator tests need no OpenCV, Tesseract or desktop session:

```sh
CGO_ENABLED=0 go test ./internal/ancientcalc
```
